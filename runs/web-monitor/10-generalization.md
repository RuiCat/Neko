## 泛化阶梯

```
具体需求      为 AstrBox 引擎添加 Go 内嵌前端网页监视器（状态/诊断/脚本/日志 + 受控写操作，WebSocket 实时）
   ↓ 泛化
任务类别      为一个长期运行的本地引擎进程做「浏览器可观测 + 受控操作」的旁路监视面
   ↓ 泛化
能力类别      监视数据面契约 / 实时通道 / 鉴权与写安全 / 内嵌资源交付 / 引擎接入与并发 /
              设计令牌 / 界面分解与元件契约 / 元件实现 / 组合装配 / 门禁与验收
   ↓ 实例化
本次能力单元  c1 数据面契约、c2 实时通道契约、c3 鉴权与写操作安全、c4 内嵌资源交付、
              c5 引擎接入与并发、c6 令牌层、c7 界面分解与元件契约、c8 元件实现、
              c9 组合装配、c10 门禁/反例/文档/验收
```

**为什么第一单元不是「写页面」**：监视器的数据来自 4 个异构源（实体树、诊断环形缓冲、注册表、日志文件），
且写操作必须与 MCP tick 共享同一把串行 gate（`internal/mcpserver/runTick.go` 的 `TryRunTick` 与
`WithStateWrite`，见 `internal/control/harness_test.go:107-130` 的并发测试）。先冻结数据面与实时帧契约，
否则前端与后端会各自发明字段名与错误语义，集成期必返工。

## 内联结论（后端能力，跨任务成立、待日后提升进域技能）

- **控制面现有接缝**：`internal/control` 已有 `/health` `/state` `/tick` `/session-event` 与请求 deadline/串行 gate
  （`internal/control/server.go:106-120`），监视器应**复用**其语义而不是重写一套；Unix socket 不能被浏览器直接访问，
  所以监视器需要自己的 HTTP 监听（用户已裁决「新增独立 HTTP 监视端点」）。
- **tick 串行化唯一入口**：`mcpserver.RunTick`/`TryRunTick` + `WithStateWrite`；任何监视器写操作必须走它，
  否则会出现「MCP tick 与页面写字段并发改同一实体」。
- **实体变更钩子**：`Entity.AddChangeListener`（`internal/entity/model.go:40-55`）是现成的增量来源；
  但它是**每实体**的，需在监视器启动时对 `ListAll()` 逐个挂、并在新实体创建时补挂（`Store.OnCreate` 已有先例，
  `internal/bootstrap/bootstrap.go:39` 提到 `store.OnCreate` 挂事件桥）。
- **日志文件事实**：tick 日志 `data/logs/state_YYYY-MM-DD.log` 是 JSONL 且**只在有 transitions/conflicts 时写**
  （`internal/engine/stateLogger.go:30-33`）；控制面请求日志 `dsh-control-YYYYMMDD.log` 是纯文本。
  两条流的格式不同，监视器不能假设统一格式。
- **诊断不落盘**：`internal/diagnostics` 是容量 512 的内存环形缓冲（`internal/bootstrap/bootstrap.go:83`），
  监视器重启后诊断清空属预期，不得承诺历史诊断持久化。
- **`go:embed` 的约束**：嵌入路径必须在包目录内且构建时存在；`design/` 真源若在项目根，需要拷贝/生成到嵌入目录，
  否则 `go test ./...` 在未生成前端产物时失败——这要求 `make` 有生成步骤或把嵌入目录纳入版本库。
